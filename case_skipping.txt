------------------------------------------------------------------------------
THE CORE REASON CASES GET SKIPPED  (one sentence)
------------------------------------------------------------------------------
When the bot reviews a case it CANNOT cleanly act on, that case stays at the
TOP of the approval queue. The bot always re-reads from the top row, so it
re-reviews the SAME stuck case over and over, burning its per-run iteration
budget (`limit`) — and every case sitting BEHIND the stuck case never gets
reached. Those behind-it cases are the ones being "skipped."

------------------------------------------------------------------------------
WHY EACH OF THOSE CASES TOOK "NO ACTION" (the exact code path)
------------------------------------------------------------------------------
In anaplasma_bot.py, after a case is found to have issues, the bot does NOT
reject immediately. It returns to the queue, RE-SORTS, re-reads the top row,
and only rejects if the top-row patient name still matches:

    if NBS.final_name == NBS.initial_name and "Out of state..." not in issues:
        NBS.RejectNotification(n)          # <-- the ONLY way the case leaves
    elif NBS.final_name != NBS.initial_name:
        print("Case at top of queue changed. No action was taken...")
        NBS.num_fail += 1                  # <-- case stays at top -> STUCK

So a case is left stuck (and re-reviewed forever) whenever:
  1. It has issues (so it is not approved), AND
  2. After returning + re-sorting, the name read at the top row does not match
     what the bot just reviewed (final_name != initial_name).

(2) happens for several real reasons:
  - The re-read happens before the re-sorted queue has settled (timing).
  - Another issue-laden case is now ahead of it, so the names differ.
  - RejectNotification itself throws (e.g. the rejection-comment window is not
    handles[2]/handles[1] as assumed in base.py:1730) and is swallowed by the
    outer try/except, so the case is never actually rejected and reappears.

A stuck case is NEVER added to patients_to_skip.txt, so nothing prevents the
bot from picking it up again on the very next iteration.

------------------------------------------------------------------------------
SECONDARY REASON — THE WHOLE RUN ENDS EARLY (mass skip)
------------------------------------------------------------------------------
anaplasma_bot.py sets:
    max_consecutive_no_case_attempts = 1

and ends the entire run the first time CheckFirstCase does NOT return exactly
"Anaplasma phagocytophilum". Seen in the logs as:
    "No Anaplasma case found. Consecutive attempts: 1/1"
    "No more valid cases found after 1 consecutive attempts. Ending run."
(3 separate runs ended this way.)

This triggers not only on a genuinely empty queue, but ALSO on a single
transient mis-read of the condition cell (td[8]) — CheckFirstCase catches
NoSuchElementException and sets condition = None, which counts as "no case."
One flaky read => the run quits => all remaining cases skipped.

------------------------------------------------------------------------------
SUMMARY OF SKIP CAUSES
------------------------------------------------------------------------------
[A] Queue-head blocking: an un-actionable case stays at row 1 and is reviewed
    repeatedly; everything behind it is skipped.        (PRIMARY, 7 cases above)
[B] Reject gated on a fragile name re-match after re-sort; mismatch => no
    action => stuck.                                    (drives [A])
[C] RejectNotification window-handle assumption can throw and be swallowed =>
    case never leaves queue => stuck.                   (drives [A])
[D] Stuck cases are never recorded in patients_to_skip.txt => re-picked forever.
[E] max_consecutive_no_case_attempts = 1 ends the entire run on the first
    non-match or flaky condition read => remaining queue skipped wholesale.

------------------------------------------------------------------------------
RECOMMENDED FIXES (not yet applied)
------------------------------------------------------------------------------
1. After reviewing a case, advance past it deterministically instead of always
   re-reading row 1 — e.g. add stuck Inv IDs to patients_to_skip for the run,
   or page by row index that increments on no-action.
2. Decouple rejection from the post-re-sort name re-match (reject the case you
   actually reviewed, by its Inv ID, not by "whatever is at the top now").
3. Make RejectNotification locate the comment window by title/URL rather than
   handles[2]/handles[1], and let failures surface instead of being swallowed.
4. Raise max_consecutive_no_case_attempts (or only count TRUE empty-queue
   results, not flaky reads) so one bad read doesn't end the run.
5. Add live per-case skip logging that appends to this file during runs (so it
   is populated automatically with Inv ID + concrete reason each run).
